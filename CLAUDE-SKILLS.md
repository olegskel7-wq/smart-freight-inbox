# SmartFreight — как применять Claude-скиллы в работе над проектом

_Памятка по dev-workflow. Скилл = сохранённый рецепт/чек-лист для Клода: он сам подхватывает
его, когда видит подходящую задачу. Вызов — `/<имя-скилла>`._

_Создан: 2026-06-24._

---

## TL;DR — что делать, по приоритету

1. **`/security-review` перед каждым мёржем в main** — твой #1 риск (cross-tenant протечка)
   и самый дешёвый страховой полис. Обязательный ритуал.
2. **Собрать кастомный скилл `/sf-feature`** под mirror-pattern проекта (через `skill-creator`) —
   окупается с первой же фичи. Первый кандидат — KB-deflection (Phase 3.9).
3. **`pptx` + `xlsx`** — под discovery-звонок и seed-демо, когда дойдёт до клиента.

## №1 — Security & quality на каждой ветке (самое ценное)

Три скилла смотрят на **уже написанный код** (текущий дифф ветки vs main) и ищут разное.
У соло-разработчика нет ревьюеров — эти скиллы их заменяют. Они **не правят код сами**
(если не передать `--fix`) — дают список находок, решаешь ты. Дополняют тесты, не заменяют:
тесты отвечают «работает ли то, что я хотел», скиллы — «что я не подумал проверить».

| Скилл | Кто это | Что ищет |
|---|---|---|
| **`/security-review`** | охранник | «через это можно влезть туда, куда нельзя?» — IDOR, cross-tenant, authz-дыры |
| **`/code-review`** | рецензент | «тут нет багов? логика верная?» (уровни low/medium → high/ultra для крупных веток) |
| **`/simplify`** | редактор | «можно чище/короче, не меняя смысл?» — reuse/дублирование (только качество, не баги) |

**Почему критично именно тут:** всё позиционирование (UK, NHS/Legal, data-residency) держится на
обещании «тенант A никогда не увидит данные тенанта B». Протечка = не баг, а смерть продукта для
регулируемого клиента. Обычный тест на «работает ли фича» такую дыру НЕ видит — её видно только
если специально искать атаку. Это твой Phase 4.7 pentest, но бесплатно и на каждой ветке (ты уже
сам добавил `CrossTenantApiAccessTest` — та же идея).

**Порядок перед мёржем:**
1. Дописал фичу на `phase3/xxx`.
2. `/security-review` → чинишь реальные находки (главный риск — endpoint берёт id из запроса, но не
   проверяет принадлежность тенанту вызывающего → IDOR).
3. `/code-review` → логические баги (null-чек, неверное условие, гонка).
4. `/simplify` → косметика изменённого кода.
5. Тесты зелёные → мёрж в main.

## №2 — Кастомный скилл `/sf-feature` под mirror-pattern (главный множитель скорости)

**Идея на пальцах:** сейчас каждую сессию Клод заново восстанавливает твои конвенции из кода
(риск дрейфа стиля — пропустить tenant-isolation-тест, забыть graceful-fallback). Скилл = записать
рецепт один раз; дальше говоришь «сделай по нему» — Клод достаёт карточку и делает точь-в-точь, без
повторного «вспоминания».

**Почему проект идеален для этого:** КАЖДАЯ фаза (2.5, 2.7, 3.1, 3.5, KB-deflection…) — одна и та же
лестница, меняется только содержимое:

```
1. V## миграция          (RLS + @TenantId, по образцу прошлой)
2. entity/               (vendor-поля типа embedding не маппятся)
3. repository/           (native ::vector где надо)
4. service/              (флаг feature.*, graceful, метрика)
5. controller/ API       (на снапшот-DTO)
6. React-страница        (зеркало /rates или /documents)
7. 5 тест-классов         (unit + standalone MockMvc + real-pgvector + tenant-isolation)
8. deploy-заметка         («realm re-import нужен только если менялся realm»)
```

**Что меняется:** пишешь `/sf-feature knowledge-base` (+ ответы на A/B-решения) → Клод скаффолдит все
7-8 файлов В ТОЧНОСТИ в твоём стиле, без дрейфа. Скилл не пишет код магически — он заставляет надёжно
повторять ТВОЙ паттерн.

**Что внутри `SKILL.md`:**
1. **Триггер** — «когда добавляем новую фичу-фазу в SmartFreight: миграция+entity+repo+service+API+React+тесты».
2. **Процедура** — те 8 шагов с правилами на каждом (флаг default-ON для операторских фич / OFF для
   тех, что шлют письма; native `::vector`; набор из 5 тест-классов; deploy-заметка).
3. **Образцы-ссылки** — эталонные файлы для копирования стиля 1:1: `entity/TrainingExample.java`,
   `repository/TrainingExampleRepository.java`, `controller/RateApiController.java`,
   `db/migration/V28__ai_feedback_loop.sql`.

**Как создать:** через `skill-creator` (скилл для создания скиллов). Утверждённый план
`C:\Users\olegs\.claude\plans\kb-deflection-plan.md` — фактически готовый черновик такого рецепта
для одной фичи; скилл обобщает его на любую будущую. Двух зайцев: собрать `/sf-feature` НА ПРИМЕРЕ
KB-deflection → и скилл получим, и первую фичу прогоним через него как проверку.

## №3 — Запуск, проверка, трение

| Скилл | Применение в SmartFreight |
|---|---|
| **`/run`** | поднять стек/приложение (`docker compose build backend && up -d`) |
| **`/verify`** | прогнать приложение и подтвердить, что фича работает в реале (часть «живых браузерных проверок») |
| **`/fewer-permission-prompts`** | Docker/maven-тяжёлый цикл → allowlist частых команд, меньше подтверждений |
| **`update-config`** | хуки/permissions в settings.json (напр. авто-`/security-review` хуком) |

## Рекомендуемый ритуал перед мёржем в main

```
1. фича дописана на ветке
2. /security-review   → чинишь cross-tenant / authz находки   ← НЕ пропускать
3. /code-review       → логические баги
4. /simplify          → косметика изменённого кода
5. тесты зелёные (целевой + при схемных изменениях — Testcontainers)
6. мёрж в main
```

Связано: `ROADMAP.md` (Phase 4.7 pentest), `CLAUDE.md` (конвенции), план KB-deflection.
